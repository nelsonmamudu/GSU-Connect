## Required safeguards before any run

1. Confirm the frontend deployment, project reference and existing live settings through read-only checks. Agree what live changes the test will make, and whether notifications, emails, scheduled tasks, webhooks and real external services can be contained. Never disable CAPTCHA or change production Auth settings merely to make a test pass.
2. Design an inventory with a unique campaign marker, reserved synthetic identifiers, collision checks, UUID tracking, retry/partial-failure handling and separately reviewed cleanup. Preserve all existing accounts and owner account. No bulk delete based on name, department or assumption.
3. Work out how a supported Auth API can create the accounts without exposing high-privilege credentials or a shared password; prefer least privilege and short duration. If a GitHub Actions secret is proposed, review workflow and repository access first, ensure no secrets in repository code, logs, artifacts or untrusted actions, and explain the access risk to the owner before setting anything. Never ask the owner to send credentials in chat.
4. Check actual signup, email confirmation, recovery and CAPTCHA constraints; admin-created identities cannot by themselves prove end-to-end signup. Use controlled email destinations only where email delivery is required; do not send to unrelated addresses. Do not bypass security controls. Unconfirmed backend features must be reported as untested.
5. Determine minimal account roles and avoid creating privileged test users until risks and scoping are reviewed. A shared password creates a common point of compromise; protect it and ensure the owner understands it is not a production-quality credential strategy.
6. Test one tagged identity and a contained scenario first. Verify inventory and cleanup behavior before scaling to 100. Avoid or explicitly mark all generated posts, chats, files, notifications and related data; no automated cleanup until separately scoped and approved.
7. Record expected versus actual outcomes and failures; no checklist box is complete unless its full criterion is independently satisfied. Real mobile hardware, delivery, calls, moderation and production data interactions require separate evidence.
