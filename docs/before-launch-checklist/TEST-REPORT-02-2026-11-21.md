## Findings requiring attention

### P84 — Funnel events can disappear or be counted twice

`src/utils/funnel.ts` sends a reference to the queue, then clears it after the asynchronous `send` completes. In a controlled local test the sender captures the original event, a second event is pushed while the request is pending, and completion clears the second event without it being sent. A separate test launches two overlapping flushes and records two sends of the same original event. The live service converts the batch to rows before awaiting the request, and both page-hide and visibility-change handlers can invoke flush. This could distort product metrics; the tests demonstrate the local race, not its frequency in production. Recommended: isolate each in-flight batch, serialize/coordinate flushes, retain later events and handle failure/retry and bounded queues explicitly, then rerun regression tests. Do not mark metrics reliable until investigated.

### P85 — An event exported at 23:30 without an end has zero duration

Using `downloadCalendarEventIcs` locally for a 23:30 event without an end time produced `DTSTART:20300130T233000` and `DTEND:20300130T233000`, despite its usual one-hour fallback. The calendar form labels end time optional. An imported calendar may therefore display the event with zero duration. The test did not import the file into an actual calendar or prove the deployed client matches this checkout. Recommended: correctly roll the end into the next date, cover boundary cases, and test imports on relevant devices.
