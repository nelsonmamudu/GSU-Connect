# Entry flow rollout — not a production deployment

**Order matters.** The new applicant and reviewer UI uses new RPCs/views. Do not roll out the whole UI against the old schema just to enroll an admin. Read `phase1-rollout.md` first. A read-only preflight on November 19 found zero approved admins with verified TOTP. Do not bypass the owner guard.

1. Back up and restore the current database (including trigger definitions, RLS, grants, Auth/session state and Storage metadata) **and object bytes** outside the repository. Rehearse against an isolated, access-controlled clone, using synthetic proof documents. Verify backups before enabling a cleanup worker. Never restore stale sessions as a rollback.
2. Make only the enrollment client available to the owner via a trusted deployment. The owner scans their own QR, verifies a code, then challenges successfully from a second session. Confirm the intended owner and recovery procedure. Keep the first session open. Share neither the QR nor the code. Only then apply the guarded `20261119_phase1_access.sql` as documented. Reps need independently confirmed cohorts, not self-reported levels.
3. Apply `20261120_entry_flow.sql` after Phase 1. This **does not seed students, auto-approve anyone, or add invited users to chats**. A rep link supplies department context only. It expires in seven days; generating another replaces it. Cases go to existing authorized reviewers only. Missing proof remains incomplete. For the 2026 pilot graduates may select the configured cohort label. Apply `20261128_graduation_class_config.sql` to move the year out of the function bodies: the cohort lives in `public.app_settings` (`graduation_class_year`, seeded `2026`) and the signup trigger, cohort trigger, review scope, level confirmation and pending-details edit all read `graduation_class_year()`/`graduate_level_label()`. The client caches the same value via `entry_config()` and falls back to `session_end_year()` for the label, so a failed RPC degrades instead of blocking signup. **To change the cohort, update that one row — never the function bodies.** Verify with `supabase/tests/graduation-class.mjs`.
4. Deploy the matching web client and Node cleanup route. Set server-side `SUPABASE_SERVICE_ROLE_KEY` and a random `CRON_SECRET` (at least 32 characters) on the deployment, and the matching public `VITE_SUPABASE_URL`. Never prefix either secret with `VITE_`, commit a value, or reuse production secrets in staging. Test that unauthenticated calls to `/api/proof-cleanup` return 401. The authenticated handler accepts **no caller-supplied storage paths**.
5. Configure two Supabase Vault secrets for that environment: `entry_cleanup_url` = its own HTTPS `/api/proof-cleanup` URL, and `entry_cleanup_token` = that deployment's `CRON_SECRET`. Check that untrusted roles cannot read Vault secrets or pg_net request headers. Apply `20261121_proof_cleanup_dispatch.sql` with pg_net available. Approval inventories *all* objects in the applicant folder in the same transaction; after commit pg_net calls the worker. Vercel Cron retries daily on Hobby. Acknowledgement checks Storage metadata after Storage API removal; SQL never deletes Storage metadata in place of bytes. Monitor nonempty/stale `phase1_private.proof_cleanup` and non-200 worker responses. A previously issued signed URL or already-downloaded copy cannot be recalled instantly.
6. Release gate on the clone: register without proof; interrupt an upload; upload, then replace proof; edit department and confirm the old reviewer loses scope; test a staff submission and AAL1/AAL2 admin; issue/rotate a rep link; test rejection and resubmission from two devices. Verify the new status signal and manual check separately (disconnect Realtime and then the network). Approve with two uploaded copies. Verify **both objects are gone via the Storage API**, the queue drains, and another applicant's file remains. Repeat with the worker temporarily offline to exercise retries. Obtain production signoff with the results.

Historical orphaned documents of **already-approved** accounts are not silently bulk-deleted by the migration. Inventory those separately and authorize cleanup after backup. Rejected/abandoned application retention is not changed by this release.

## Local verification

`npm run test:entry` runs the PostgreSQL policy/queue fixture, OCR parser tests, and a mocked Storage API retry test. `npm run lint` and `npm run build` verify TypeScript and asset packaging. The PostgreSQL engine does not emulate GoTrue, hosted Storage, pg_net delivery, or a live Realtime subscription. The OCR worker, English model, WASM and PDF worker are bundled locally; the proof is never sent to a third-party OCR provider. PDF assistance reads the first page; unreadable, encrypted, multi-page or unlabelled evidence can still be submitted with manual details.

### Private owner binding and staff review — staged, not authorized for production

1. **Lockout risk:** the owner cannot be demoted, suspended, expired, transferred or deleted by normal application flows. Losing Auth access or the second factor can lock out exceptional administrative access. A database operator with DDL privileges is outside this guarantee. Agree on an independently authenticated, offline recovery procedure first. Do not weaken the binding to troubleshoot login.
2. Before enforcing Phase 1 or applying the owner migration, take and verify a restorable backup, independently verify the intended Auth UUID and its approved non-expiring admin profile, enroll that account in TOTP, then prove fresh sign-in and step-up from another session. Never commit the UUID or TOTP secret. Rehearse migrations against a disposable schema copy first, including policies and helper definitions; stop on drift. Set `gsu.verified_owner_id` in the *same database session* used for migration 20261122. It aborts rather than choosing an admin by name or signup order. Do not run an unattended production migration push.
3. Coordinate database, web and `staff-email` Edge Function versions. Configure the existing verified Brevo sender (`BREVO_API_KEY`, `BREVO_SENDER_EMAIL`) and canonical HTTPS `APP_URL` server-side. Never ship the service key in the client. Check the free sender quota and delivery to a real university inbox. Open the link as the requesting applicant, including a logged-out/mobile round trip. A confirmed mailbox proves control, not employment; admins still review. Confirm the institution actually reserves the allowed domain for staff before launch.
4. Existing approved staff keep access but do not automatically become vouchers. Bootstrap using independently reviewed documents or confirmed institutional email. Test a pending applicant, a scoped reviewer, a verified same-department witness, an AAL2 admin and the enrolled owner in separate sessions. Check actual Storage metadata, restricted proof visibility, in-app vouch delivery, evidence cleanup, audited override, and denial of transfer/deletion. Keep a verified admin available for ordinary reviews. Do not roll back by dropping the owner guard on a live system.
